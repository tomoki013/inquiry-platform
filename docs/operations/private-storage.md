# Private storage

Deploy Core and mail-ingress with the same `PII_ENCRYPTION_KEYS` Worker Secret. Its format is `keyid:base64url-32-byte-key[,oldid:old-key]`; the first key encrypts, all listed keys decrypt. Core also requires an independent random 32-byte base64 `PII_HASH_KEY` for Push endpoint equality checks. Set `PII_REQUIRED=true` in production; a missing encryption key then refuses private operations rather than storing plaintext. Keep recoverable copies of keys outside the database and repository with restricted access. Restoring the database without its matching keys cannot restore private content.

Core encrypts contact identities, subjects, messages, drafts, internal notes, report details/snapshots, private event copies, filenames, operator notification destinations and Push credentials before D1 writes. AES-256-GCM uses a fresh IV and authenticated, project-derived HKDF keys. Key IDs and project scope are authenticated; R2 payloads and private metadata are bound to the object key. Public project catalogue data, status codes, routing IDs, timestamps, aggregate counts and notification payload IDs remain readable. Event metadata generated by SQL triggers may contain only IDs/codes and encrypted copies; repository-created free text metadata is encrypted.

Repositories declare private parameters explicitly. The native database boundary decrypts each result once. Project adapters still enforce the registered project's physical tables and permissions; encryption does not replace authorization. Support search scans only authorized candidates and decrypts before matching. It preserves substring search and pagination but may cost more reads for large inboxes. Sender identity checks compare decrypted addresses after resolving trusted receipt/thread references.

## Existing deployments

1. Back up the database and separately retain the keys. Apply forward migration `0020_private_push_index.sql` before deploying new Core code.
2. Register the secrets on Core and mail-ingress, enable required mode, then deploy both. Dual reading keeps old plaintext records and unmarked files readable while new writes are protected.
3. Invoke `POST /internal/privacy/backfill` with JSON `{ "project": "example-project" }` through a temporary, authenticated **unscoped Core service binding**. This route is unavailable to scoped clients and has no public Core route. Repeat until `{ rows: 0, files: 0, done: true }`. Responses contain counts only. The endpoint requires active registered project storage.
4. Each call migrates a bounded batch using original-value comparisons. Active and retained legacy copies are included. Legacy triggers are suspended and restored within one atomic D1 batch so their write fence is never absent at commit. Original business triggers must not manufacture new legacy writes during encryption.
5. Referenced attachments and inbound journal files for the project are encrypted with etag comparisons. A journal list exceeding 1,000 objects refuses completion and requires explicit pagination work; it never silently skips the excess.
6. Completion installs plaintext rejection triggers on active private columns and shared notification/Push storage. Verify aggregate plaintext counts are zero, normal authorized reads work, and a repeat call is done. Remove the temporary caller afterward. Do not roll back to an old plaintext writer after sealing.

Public support addresses and mail signatures are deployment settings. A private notification recipient should normally use a Worker Secret fallback. After sealing, offline seed SQL that tries to write a plaintext `notification_email` is rejected; omit that override and use the Secret, or supply an encrypted value from a controlled operator process.

Key rotation prepends a new encryption key while retaining older keys until every retained record, file and backup has been rewritten or expired. The HMAC key must remain stable while its endpoint indexes are in use. SQL-readable old values in Time Travel, provider backups and mail providers are separate retention scopes; encrypting current rows does not rewrite those histories. Key loss or removing an old key early is data loss.
