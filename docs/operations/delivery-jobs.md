# 配送・受信処理の復旧（v0.8.0）

`0014_delivery_jobs.sql` を適用する。新着メール通知、Push通知、受信メールの取り込み、障害通知を既存のD1で管理する。Ticket作成と通知ジョブの保存は同じトランザクションで行う。

## 処理と再試行

- `queued` → `running` → `completed`。例外時は静的な理由コードを保存し、1・2・4・8・16・32・60分の間隔で、初回を含め最大8回試す。既存の5分Cronで再開するため、実際の実行はCronの周期に従う。
- 実行権は10分のleaseで確保する。同時実行や古いWorkerからの完了通知は、lease tokenで排除する。期限切れの8回目は`failed`にする。
- メール通知は既存のプロバイダ冪等キーを使う。Pushでは成功・失効した宛先を記録し、通常の再試行ではその宛先に再送しない。プロバイダの成功とD1への記録の間で停止した場合まで、配送の厳密な一回性を保証するものではない。
- 初回失敗ごとに障害通知を予約する。同じ手動再試行の世代では一通にまとめ、障害通知自身の失敗から新しい障害通知は作らない。元の処理が復旧した、または世代が変わった場合は古い通知を送らない。
- 障害通知には処理種別・Project名・管理画面リンクだけを載せる。本文・件名・メールアドレス・添付・生の例外やプロバイダ応答は一覧、監査、ログに出さない。

## 受信原本

mail-ingressにもCoreと**同じ既存のprivate R2**を`PRIVATE_FILES`としてbindする。転送後、最大5MiBの原本を保存してからCoreへ引き渡す。Coreが停止していた場合も、CronがR2の原本から失われたジョブを復元する。新しいbucketやQueueは不要。

`inbound-jobs/`は公開しない。原本は取り込みと添付の保存が完了した後に削除し、未完了でも30日後に削除する。期限切れは`MAIL_EXPIRED`として一覧に残し、手動再処理を拒否する。完了ジョブは90日後に削除するが、未復旧の障害通知の重複防止記録は保持する。

5MiBを超えるメールは従来どおり転送のみで、原本を保存せず取り込みを行わない。転送のSMTP再送はこのジョブの対象外。R2自体への保存失敗はmail-ingressのログに残り、先に転送したメールから復旧する。

## 管理API

`GET /api/deliveries`は未完了の先頭100件と総数を返す。`POST /api/deliveries/:id/retry`は失敗、またはエラー付き再試行待ちの処理を予約し、操作者を監査する。閲覧は`read`、再処理は`operate`権限が必要。実行中・完了済み・原本期限切れは409。

Project管理画面ではSDKの`ProjectOperatorClient.listDeliveryJobs`と`retryDeliveryJob`を使う。Service Bindingのpropsで許可されたProjectだけが対象で、他Projectのジョブは`NOT_FOUND`となる。

## 反映・復旧

1. D1をprivateにバックアップし、直前のWorker versionを記録する。
2. SDK/coreの参照をv0.8.0へ固定し、mail-ingressに共有R2 bindingを追加する。
3. デプロイ設定で`check`、`migrate`、Core → gateway → mail-ingressの順に`deploy`する。その後に利用側のAPI・管理画面を反映する。
4. 復旧時は旧Worker versionへ戻す。追加テーブル・未処理の原本は削除しない。旧コードでは再試行が止まるので、修正版を反映後に復旧する。

マスタ設定の`ticket.settings_updated`監査にも、変更前`from`と変更後`to`を保存する。記録は変更と同じD1 batch内で行い、旧形式の監査も引き続き読める。
